## Exact test boundary

1. Reuse `scripts/test-pages-provider-fixture.py`'s fresh pinned GoTrue/PostgREST/PostgreSQL pair and synthetic `example.test` owner. Keep all three services on the existing internal Docker network with zero published ports. Reuse the allowlisted persistent Docker-private fetch transport from `tests/integration/auth/private-provider-fetch.ts`; do not create a second provider protocol implementation.
2. Add a test-only HTTPS gateway bound to `127.0.0.1` on an ephemeral port. Generate a one-run CA and `127.0.0.1` leaf certificate in the owned temporary fixture directory using the installed OpenSSL, with no certificate-key output. The gateway must accept only loopback clients, exact Host, bounded request bodies, and the already allowlisted Auth/RPC methods and paths; forward through the existing private transport. It must not publish database, GoTrue, or PostgREST ports.
3. Start `wrangler pages dev` for the existing 26-page export on a second loopback port. Give Wrangler a minimal child environment with `APP_ORIGIN`, `SUPABASE_URL=https://127.0.0.1:<gateway-port>`, synthetic publishable/service keys, `SESSION_CRYPTO_CONFIG_JSON`, fixed local trusted caller, and `NODE_EXTRA_CA_CERTS=<one-run CA>`. Use Wrangler's documented `CLOUDFLARE_INCLUDE_PROCESS_ENV=true` local binding path with no `.dev.vars`/`.env` in the Pages directory. Never place keys in command arguments, a repo file, logs, or the receipt. Do not disable TLS verification or alter the production HTTPS-only origin check.
4. Drive the **actual HTTP Pages Function** through denied origin/method, login, strict cookie/CSRF read, refresh, role change, logout and post-logout denial. Confirm the private BFF/Auth SQL row state, no-store/privacy headers, no secret reflection, and exact owned-resource cleanup. Capture only sanitized status/timing/count/CA-fingerprint evidence. A negative TLS-trust control should fail closed if practical without weakening the final run.

Reuse the documented pinned Node and installed OpenSSL; do not edit the app Pages Functions, production auth, locked UI, Docker fixture or existing migration.

The probe first verifies the HTTPS server with an explicit trusted-CA Node client. ## MP-08n.3b — actual provider lifecycle after runtime diagnosis

The initial full run still failed at login 503. Count-only tests then isolated two real Workerd differences: `redirect: 'error'` makes an outbound fetch fail before the target receives it, while `redirect: 'manual'` reaches it; and Workerd's native `fetch` fails if called as a method of an arbitrary holder object, while a local function reference succeeds. The [pinned-date probe](evidence/MP-08n3a-pinned-date-probe.txt) and [full-manual probe](evidence/MP-08n3a-full-manual-probe.txt) record the redirect result. A temporary local Function, now removed, verified binding shape and the receiver difference in the actual Pages project; only count/status markers were retained in the failed diagnostic receipts.

The server-only Auth transport and service RPC now request `redirect: 'manual'`; both reject a 3xx response under their existing status checks, so credentials are not sent to a redirected target. The RPC adapter calls its injected `fetch` through a local function reference. Focused tests include the receiver regression and redirected-response rejection. The test-only TLS gateway now uses Node's HTTPS server and verifies a trusted local request as well as a no-CA negative control. The SQL oracle now compares the exact pre-existing `auth.sessions` ID set: synthetic signup creates its own provider session, which BFF logout must not revoke.
