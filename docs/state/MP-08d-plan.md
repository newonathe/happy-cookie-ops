# MP-08d — persistent-session design and encrypted token envelope

Status: local crypto implementation and verification complete. Persistent SessionAuthority remains incomplete.

## Persistent authority contract to implement next

Use a server-only session repository, never a process-global map. Store the SHA-256 hash of a32-byte random opaque cookie identifier; retain its plaintext only in the secure cookie/current request. Generate an independent32-byte CSRF token. Session maximum lifetime remains8hours, enforced server-side and never extended by refresh. The browser receives neither provider token. A session record must bind user ID, provider session ID, absolute expiry, credential version and encrypted provider-token envelope. Read authorization must check active profile, local revocation and authoritative provider session existence; an expired access JWT must not make an otherwise valid refresh impossible. Validate provider session binding through authenticated provider evidence before creating a row; simply decoding unverified JWT claims is insufficient.

Use PostgreSQL for durable refresh fencing, with a unique session hash and transactional compare-and-swap version. Acquire a finite lease and monotonic fence before calling the remote refresh endpoint; only that fence may finalize credentials, and revoked/expired rows cannot be revived. Concurrent requests fail unavailable or use a finalized current record; never independently refresh the same stored token. A provider request with uncertain outcome requires explicit recovery/re-authentication; timeout does not prove rollback. A stale worker cannot release or finalize another worker's lease. Keep the opaque cookie and CSRF stable across routine provider refresh so a lost response does not strand the browser; mint a new session for a new login. Logout marks local revocation before remote cleanup; provider failure remains503 and a later read rejects the locally revoked session. Keep enough restricted encrypted cleanup material until provider revocation is acknowledged or expired; never authorize from a cleanup record.

The persistence migration and its narrow server-only RPC authority require real SQL tests before acceptance. No broad service-role table proxy; ordinary business RPCs still execute under the user's JWT and active-profile checks. Existing fail-open public rate limiter cannot authorize login: preserve its single rule catalog but add a fail-closed adapter with trusted deployment identity when integrating. Database outage must not bypass auth or throttling. Owner/staff provisioning, MFA, recovery, return path, Pages bindings, CPU and actual Apple browser evidence remain explicit later acceptance requirements.

## Storage acceptance checklist for the next migration packet

- Dedicated session schema/table and fixed functions, no anonymous/authenticated table or function grants; restricted server infrastructure authority only. The session row contains no plaintext cookie or provider token. Use foreign keys and exact constraints for user/provider IDs,64hex session hash, key-envelope bound, absolute expiry, nonnegative safe-integer version/fence and enumerated lifecycle.
- A read proves active profile and authoritative provider session identity/existence even when access-token time has expired. Missing/revoked/provider-deleted/expired rows return no authenticated record. Renewal may update provider credentials, never original absolute expiry. On reauthentication create an independent opaque identifier and CSRF token.
- Acquire/finalize/revoke operate transactionally with row locks and compare-and-swap fence; race refresh versus refresh, revoke versus refresh, expiry versus finalization and profile deactivation versus command. A timed-out refresh lease is an uncertain external operation, not permission to blindly reuse the old refresh token. Require reauthentication unless a reviewed provider-specific recovery protocol proves safety.
- Read and finalize must not trust a client-provided role, user ID, version, expiry or provider-session UUID. The BFF derives all identities from verified server evidence. Staff domain operations retain JWT/RLS and transaction-time capability checks independent of this infrastructure authority.
- Prove logout denies the next BFF request before remote cleanup. Record cleanup state safely and make retries idempotent; no success acknowledgment if remote revocation is unresolved. Cleanup material cannot reopen a locally revoked session.
- Fail closed on repository, rate limiter, crypto/key or provider outage. Keep raw exceptions and all password/token/key/envelope values out of logs/error JSON. Correlation IDs and minimal action/status telemetry only. No credential-bearing URL or referrer.
- Test a full session from login through read, expiry, role change, refresh conflict, lost response, logout and recovery against the actual provider plus disposable PostgreSQL; fake-authority tests are only local boundary evidence. Generate types and compare schema over two owned resets. Until Docker recovers these are NOT_RUN.

## Independent design review refinements

Refresh finalization must verify the returned provider identity and session identity against the row's bound userId/providerSessionId before persisting any new envelope. Equality of the projected UI profile alone is insufficient; neither caller IDs nor a merely decoded JWT satisfy this oracle. Unexpected identity changes revoke/deny the operation, never relabel a session. Use PostgreSQL server time for every lease, absolute-expiry and finalize condition; an application clock cannot extend the deadline or steal a live lease. Fencing checks remain mandatory even if an application AbortSignal has not fired.

The identifier hashing helper rejects noncanonical encodings. The eventual authority must map a malformed browser cookie to unauthenticated401 without treating a configuration/key failure as an invalid credential. Keep these error origins separate during integration.
