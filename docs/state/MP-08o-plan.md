# MP-08o — expired-session cleanup and bounded scheduled caller

Status: MP-08o.2, MP-08o.3 and MP-08o.4 accepted on pinned local fixtures, 2026-09-25. G1 and parent MP-08 remain open. The scheduled adapter has no hosted deployment, configured Cron trigger or production secret binding.

## Why this needs stages

- `bff_session_claim_cleanup` fences expired active sessions and pending retries, but the current selection orders by oldest absolute expiry. `claimCleanup()` processes the claimed rows sequentially and stops on first provider failure. A repeatedly failing old row can starve newer claims. The existing SQL migration is applied and must stay unchanged.
- Provider access tokens expire before the eight-hour BFF absolute lifetime. Current cleanup calls provider logout with the stored access token; its behavior after expiry is unverified. Do not clear an encrypted credential envelope merely because the access token is rejected. The fenced `bff_session_complete_cleanup` remains the only clearing path after confirmed provider revocation.
- A Cron Trigger is a plausible free-tool caller independent of whether the public app lands on Pages or Workers. Cloudflare currently documents a scheduled Worker handler, local scheduled-event testing, five free Cron Triggers per account, 10 ms free CPU and 50 external subrequests per invocation. These are limits to measure against, not proof this code fits. Deployment waits for the account, platform decision and explicit hosted authorization. See the [Cron Trigger guide](https://developers.cloudflare.com/workers/configuration/cron-triggers/) and [limits](https://developers.cloudflare.com/workers/platform/limits/).

The root agent independently reran the tightened script; [sanitized receipt](evidence/MP-08o1-expired-provider.txt) records exit 0, no published ports and guarded cleanup. This establishes a necessary recovery path but does **not** make current cleanup safe: refresh rotates its credential, so a later logout failure requires durably saving the rotated credential behind a fence before retry. Do not call the current `claimCleanup()` on expired rows as an accepted production fix.

Cloudflare scheduling and the app hosting choice remain separate from this provider behavior. Next implementation design must prove a fenced rotation-save operation on a revoked row, same user/session binding, retry fairness and behavior when refresh itself is denied. No applied migration is edited; no encrypted envelope is discarded before confirmed revocation.

The recovery design has a real crash window: Supabase refresh tokens are one-use, so GoTrue can rotate the token and return a new pair just before the Worker fails, before the new encrypted pair is persisted. A compare-and-swap save after refresh reduces stale writes but cannot make the remote refresh and PostgreSQL save one transaction. The next slice must explicitly handle that uncertain outcome, for example by confirming whether the exact provider session still exists and defining a safe terminal/manual path if it does. Do not assume a failed refresh proves provider logout, delete a user or all their sessions, or silently discard an envelope. The [Supabase sessions guide](https://supabase.com/docs/guides/auth/sessions) documents one-use refresh tokens and session-row semantics; the pinned GoTrue fixture supplies the local measured behavior.

## MP-08o.2 prerequisite — direct-parent refresh recovery, 2026-09-24

**PASS for the pinned local provider behavior only.** A fresh private GoTrue/PostgreSQL fixture rotated the original refresh token, waited 11 seconds, then submitted that exact original token again. The provider returned HTTP 200 and the **same child refresh token**; all issued access tokens retained the original user and provider-session IDs. Local logout with the replayed access token returned 204, removed exactly that provider session, left a second session of the **same user** intact and usable, and subsequent `/user` for the revoked session returned 403 `session_not_found`. See the [test-only probe](../../scripts/test-refresh-parent-reuse.py) and [sanitized root rerun](evidence/MP-08o2-parent-reuse.txt). The [Supabase sessions guide](https://supabase.com/docs/guides/auth/sessions) describes a direct-parent reuse exception; the [pinned GoTrue v2.196.0 token service](https://github.com/supabase/auth/blob/v2.196.0/internal/tokens/service.go) returns the currently active child when the submitted token is its direct parent. The fixture establishes that this worked beyond the usual short reuse interval for this exact local version; it does not establish a hosted-version guarantee.

This narrows, but does not eliminate, the remote-refresh/local-save crash window. The stored token remains the direct parent if **this BFF is the only refresher for its revoked provider session** and the cleanup attempt performs at most one rotation before durably saving the child. On a subsequent attempt, that parent can recover the active child on the pinned version. A provider-version change, external use of the token, unexpected additional rotation, or inability to reach the provider can break that premise. Such failures must keep the encrypted envelope and surface an alert; neither a refresh denial nor an HTTP timeout proves revocation.

### Concrete o.2 implementation contract

1. Add a **new migration**, never modify the applied private-session migration. `bff_session_save_cleanup_rotation` is a service-role-only, `search_path = ''` security-definer RPC. It validates the session hash, nonnegative fence/version, expected user and provider-session UUIDs, and bounded nonempty encrypted envelope. It atomically changes only a `state='revoked'`, `cleanup_state='pending'` row whose fence, stored version, user ID and provider-session ID all match; increments the credential version by exactly one and returns one row or none. A stale claimant cannot overwrite a newer credential. Use the same object ownership, explicit PUBLIC/anon/authenticated revokes and service-role grant conventions as the existing migration. Its envelope is opaque ciphertext; the RPC never accepts a raw token.
2. Add a service-role-only `bff_session_complete_if_provider_absent` RPC. Under the matching revoked/pending row fence and exact stored user/session binding, check the **managed** `auth.sessions` row by its `id` alone before clearing anything. An ordinary present row returns zero rows. A row with that ID but unexpected `user_id` raises a **static, identifier-free binding-mismatch error** for operational investigation and leaves the envelope pending; a predicate that checks `id` **and** `user_id` in `NOT EXISTS` would falsely treat that mismatch as absence. Only if no row with the ID exists, atomically null the envelope and set `cleanup_state='complete'`/completion time. Return zero rows if the BFF row or fence is stale or its binding differs. Keep the read/check/update within one database transaction; do not delete or modify managed Auth rows. A database/query error must remain an error, never an absent result.
3. For a claimed row, decrypt its envelope with the stored version and first try local provider logout with its access token. On confirmed 204 or the pinned exact `session_not_found` response, complete with the current fence. Extend the Auth transport with a **typed, exact 403 `bad_jwt` logout denial**; do not infer its cause from the code or expose raw provider text. Only on that denial, refresh once using the encrypted refresh token. All other logout errors stay fail-closed. Before any logout with the new access token, call the existing Auth `/user` binding check and require **both** expected user and expected provider session. Seal both new tokens with version + 1 and persist them through the new rotation RPC at the current fence. If the save returns no row or errors, stop; do not logout or clear the envelope. If it succeeds, logout with the new access token, then complete at the same fence. Never refresh a row twice in one claim.
4. If refresh is denied or its result/binding cannot be trusted, try the exact-row absence RPC. Treat one returned row as durable completion, zero rows as still-pending operational failure. If refresh or logout has an ambiguous transport result, absence verification may resolve a proven gone session; otherwise keep the pending envelope. A newer claimant may recover a direct parent. A permanent still-present session with unusable credentials is an alert/manual-recovery case, not a reason to delete the user, revoke all sessions, or discard credentials.
5. Implement cleanup outcomes per row so one failure cannot abort already claimed later rows. Give each row an independent bounded timeout/controller while respecting a separate overall invocation deadline; a timed-out row must not abort the signal used for the next row. Stop on an aborted overall invocation or exhausted provider subrequest budget. Record only allowlisted aggregate counts and error classes, without session hashes, user IDs, token values or envelopes. The new fair-claim migration in o.3 must also prevent the same old row being reselected ahead of later eligible work; per-row continuation alone does not solve cross-tick starvation.

Required acceptance before wiring a scheduler: SQL fixtures for stale fence, version, BFF user/session mismatch, present/absent provider row, **existing Auth row with matching session ID but unexpected user ID**, privilege boundary, concurrent claims and opaque-envelope non-disclosure; authority tests for unexpired logout, expired refresh/rotation/save/logout, save failure, provider timeout before/after remote rotation, refresh denial with present/absent Auth row, one bad row followed by a good row, and a hung row followed by a good row under independent per-row deadlines; at least one disposable real-provider lifecycle with an injected post-refresh/pre-save interruption and retry after the parent reuse interval. Prove empty commercial data, no published ports, managed Auth-schema integrity and exact owned-resource cleanup. Regenerate typed RPC declarations and manifests as the existing migration workflow requires. Run pinned `pnpm verify`, continuity and fixture guards. None of these implementation gates are claimed by the parent-reuse probe.

The new migration is a deliberately atomic repository-wide schema slice: the current disposable database bootstrap and Auth fixture each assert **exactly 24** reviewed migrations; session-repository and Pages/provider fixtures also pin the count, and the Auth fixture hashes each migration in its source-pin manifest. Before claiming the SQL slice passes, update those explicit 24-to-25 assumptions and add only the new migration's hash; retain all earlier hashes and historical 24-migration receipts. Regenerate public database types and the function-authority manifest from the fresh owned fixture, then prove every fixture still guards against unreviewed source drift. Adding a migration without this coordinated pin/type/test update would intentionally fail the existing safety harness, so it is not a usable intermediate checkpoint.

## MP-08o.3 fair cleanup claims — 2026-09-25

The new, unapplied [26th migration](../../supabase/migrations/20260101002500_bff_cleanup_fair_claims.sql) changes only the eligible candidate order in `bff_session_claim_cleanup`. A never-claimed active row sorts by its absolute expiry; a never-claimed revoked row sorts by the earlier of revocation and expiry; a retry sorts by its last cleanup attempt. Expiry and session hash break ties. A failed claim advances its sort time, so an already-waiting good row can precede it on a later tick, including when `p_limit=1`. The original 30-second retry floor, `FOR UPDATE SKIP LOCKED`, limit, fences, result projection, owner, restricted grants and empty function search path are preserved. This is a progress policy, not a fixed latency promise under an arbitrarily large older backlog. No new index was added without query-plan evidence. The migration SHA-256 is `0ad8ec77d1963e5a2a70bcf1680a8044b260a393af5a06bacba5d5a198bd327b`; all earlier pins retain their hashes.

The first null-first ordering was rejected after independent Sol/high review because sustained new arrivals could starve retries. ## MP-08o.4 local scheduled adapter — 2026-09-25

The new [scheduled Worker](../../spikes/cleanup-worker/src/index.ts) composes the existing persistent authority, Auth transport, crypto and typed service RPC. It has no public `fetch()` handler and [its config](../../spikes/cleanup-worker/wrangler.jsonc) has `workers_dev=false` and no Cron trigger, so no schedule or public route is activated. A tick makes one three-row claim and caps outbound fetch attempts at 40, leaving headroom below the documented free-tier 50-subrequest limit. Its own 24.5-second wall deadline aborts the authority's 25-second deadline; the authority still gives each claimed row a six-second deadline. Only HTTPS provider origins, shaped `sb_secret` and publishable keys, and a valid crypto configuration are accepted. The event log contains aggregate counts or one static failure class, never identifiers, credentials or provider messages. A batch with failed rows logs `partial_failure` and makes the Cron invocation fail, leaving database-led retry for a later tick.
