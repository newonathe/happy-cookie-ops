## Default privileges: verified semantics and deployment decision

The old inventory recorded ACL text/creator/object kind but omitted schema scope. Use the new [scoped experiment](evidence/MP-06b-defaults.json) for that distinction. Query pg_default_acl including defaclnamespace and creator; include all scopes, not only public. Current owners show present ownership, not a complete history of original creators or proof of future deployment identity. The fixture records current_user/session_user; hosted identity remains unverified because no hosted database exists.

The [PostgreSQL 15 documentation](https://www.postgresql.org/docs/15/sql-alterdefaultprivileges.html) establishes that defaults apply to future objects made by the specified creator. Global and per-schema grants add together; a per-schema revoke cannot cancel global PUBLIC EXECUTE. Existing objects need their own revocations. Different creators require their own default configuration. The experiment verifies these distinctions locally, including creation in another schema and by a separate temporary NOLOGIN role.

Proposed minimum for future postgres-created public RPCs is a creator-global PUBLIC EXECUTE revoke plus a public-schema anon/authenticated default revoke, retaining explicit service-role grants only where needed. This is a candidate, not an applied change: the global revoke also changes future postgres-created functions in managed/extension schemas. Do not alter supabase_admin defaults just because its catalog entry exists, and do not infer a public-only effect from a global command.

Before the default migration is executable, a dedicated slice must: inventory the actual deployment creator and role memberships; establish who creates auth/storage/extensions objects during supported upgrade/install flows; test those flows with the candidate defaults in isolation; enumerate intentional public/role function grants; test future public functions, existing functions, other schemas and other creators; and add a migration review guard that rejects new unreviewed functions/grants. Unexpected creator/scope fails closed with a precise setup action. A dedicated application migration owner is an alternative if managed-schema compatibility cannot be established, but requires its own ownership/membership/CLI rehearsal. Do not silently introduce that architecture or mass-transfer existing ownership here.

Table/sequence defaults are a separate slice: inspect inherited anon/authenticated INSERT/UPDATE/DELETE/TRUNCATE/REFERENCES/TRIGGER and sequence permissions, then replace broad defaults with explicit grants for reviewed projections/commands. RLS is not a substitute for table privilege review. Keep current-object revocation separate from future-object defaults so tests identify the responsible change.
