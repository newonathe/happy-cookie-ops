# MP-08g — authentic local Auth fixture before session persistence

Status: implemented and locally verified on 2026-09-21. The bounded managed-schema prerequisite passes on two fresh pinned GoTrue/PostgreSQL pairs with no published host ports and verified cleanup. This is **schema metadata only**; the BFF session repository, HTTP Auth lifecycle, revocation/refresh races, hosted integration and G1 remain incomplete.

## Exact scope and boundary

Build a separate, disposable local fixture that runs the cached pinned GoTrue/Auth image against its own pinned PostgreSQL image, then run the existing `tests/integration/auth/provider-session-preflight.sql` unchanged. Do not connect to a hosted project, create a real owner account, read session/user/token rows, add a compatibility `auth.sessions` table, or run SQL against the owner's normal local project. The output may contain relation/column/index metadata and image/version digests, never generated JWTs, passwords, API keys, email addresses, rows or full CLI stdout. Keep the existing bare-Postgres MP-05/06 harness unchanged; it remains the correct fast fixture for public schema/role tests.

## Owned fixture design

1. Create a fresh random `hcb-auth-*` workdir only beneath `C:\Users\ethan\dev`, with a one-time `owner.json` containing its exact project ID. Reject symlinks/junctions and any path outside that parent before cleanup. Copy only reviewed application migrations; no seed, `.temp` project link, remote URL or external credential. Resolve the already cached PostgreSQL 15.8.1.085 and GoTrue 2.196.0 image tags to immutable local image IDs before any create. Stop if either image/version differs from what the provider contract review accepts.
2. Preflight Docker's `default` context and pinned Windows named pipe. Refuse collisions in exact container/network/volume names and labels. Create a uniquely labeled private bridge network and exactly two labeled containers from the captured image IDs. **Publish no host ports at all** for either service; use no host bind mounts. This is the pre-start isolation guarantee. GoTrue must actually start and initialize its managed Auth schema using generated local-only DB/JWT secrets passed only through child environment; never write or print those values. Review the pinned image's required environment and startup contract before coding this step.
3. Capture both container IDs before start. Inspect exact label/name/image/mount/network attachment and `HostConfig.PortBindings` **and** `NetworkSettings.Ports` before starting and again after startup; both must have no published host bindings, including IPv6/wildcards. Reject unexpected containers or network endpoints. A failed assertion stops the fixture before SQL, then invokes only guarded owned cleanup. Do not run `supabase start` on this Windows host: the earlier MP-05.a live reproduction showed its custom-bridge setting still produced `0.0.0.0` and `::` publications. Post-start checks alone would discover exposure too late.
4. Wait for actual GoTrue health/migration completion on the private network. Feed the 23 public application migration files in exact order to `psql` through `docker exec -i` on the captured database container; do not claim this is a Supabase CLI reset or manufacture CLI migration history. Verify each file hash against the reviewed source pins, final public catalog and zero demo transactions. Compare a schema-only Auth dump before and after application migrations for structure, grants, policies and triggers. The pinned migration corpus has no Auth-targeting DML/DDL in source review; the dump alone cannot prove the absence of transient Auth row writes. Run the pinned read-only metadata preflight through that same owned container with short statement/lock timeouts and rollback. Require the exact `auth.sessions`/`auth.users`/`public.profiles` column types, nullability and single-column primary key. A passing static schema check is only permission to design the migration; it does not prove token refresh, revocation or managed Auth behavior.
5. Repeat on a second **fresh owned pair of containers and network**. Metadata and image IDs must match. Never count two reads of one database as two independent clean initializations. Remove only captured, re-inspected owned container IDs, then the exact labeled network after zero endpoints, then the verified workdir. Confirm no owned containers, network, volumes or workdir remain. If identity or cleanup fails, retain uncertain resources and report FAIL; never use `docker prune`, `supabase stop --all`, or a wildcard delete.

## Verification and stop conditions

- Add negative tests for wrong root, mismatched owner marker, junction/symlink, project collision, **any** published host port, unexpected image/resource/network endpoint, missing managed relation/column/primary key, startup failure, timeout, partial output and cleanup failure. Every failure must stay non-authorizing and preserve evidence without leaking credentials.
- A passing result requires two fresh managed-schema initializations, identical bounded metadata, exact cleanup receipts, port/engine integrity, `pnpm verify`, and independent security review of the fixture. Check actual image digests; do not assume today's upstream documentation matches the pinned local image.
- Stop before writing the session-storage migration if `auth.sessions.not_after`, the required binding, or cleanup ownership fails. Do not substitute the upstream source schema for measured local metadata. The subsequent repository slice must separately prove races, expiry, revocation, no token plaintext, API denial and real Auth HTTP behavior as specified in [MP-08e](MP-08e-plan.md).

[Supabase's local development guide](https://supabase.com/docs/guides/local-development) recommends a loopback-bound Docker network for its CLI stack. On this actual Windows Docker Desktop installation, [MP-05.a's live evidence](MP-05a-plan.md) showed that the recommendation did not constrain published bindings. The no-published-port private-network design above superseded the initial CLI-start proposal. An early unsafe scratch runner was removed before execution. The accepted runner uses an internal bridge, checks Docker's observed network/port state before start and after start, and runs no Supabase CLI stack.

## Local execution and evidence — 2026-09-21

The accepted [runner](../../scripts/test-auth-fixture.py), [15 guard tests](../../tests/unit/test_auth_fixture.py), [23 source and preflight pins](../../tests/fixtures/mp08g-source-pins.json), and [read-only metadata SQL](../../tests/integration/auth/provider-session-preflight.sql) are separate from the fast MP-05/06 bare-database fixture. The runner creates two fresh owned internal-network pairs, initializes GoTrue's managed schema, applies the 23 pinned public migrations without seed data, compares before/after Auth schema-only dump hashes, checks all five transaction tables contain zero rows, and executes the preflight. GoTrue's dedicated `supabase_auth_admin` login is initialized only inside each disposable database using the generated local password. The SQL preflight now requires single-column `id` primary keys on all three checked relations.

[Final live receipt](evidence/MP-08g-live-final.txt) is PASS: two distinct run IDs, matching Auth/public metadata and image IDs, 23 exact migration hashes, `auth.sessions`/`auth.users`/`public.profiles` metadata, internal-bridge/zero-published-port checks before and after start, and zero owned containers/networks/workdirs after cleanup. [Focused guards](evidence/MP-08g-guards-final.txt) and [repository verification](evidence/MP-08g-verify-final.txt) are the application gates. Earlier attempts 1–8 document harness startup and diagnostic corrections; [attempt 9](evidence/MP-08g-live-attempt9.txt) passed before the independent review requested source pins, broader Auth schema checks and per-pair receipts. No failed attempt was accepted as schema evidence, and all owned resources were rechecked as absent after the final run.

Independent Sol/high review verified the source pins, three-relation parser/PK assertions and the final receipt, and identified one limitation: schema-only dumps cannot detect transient row DML. Root audited the exact 23 pinned migration bodies with targeted `auth.`/`search_path`/dynamic-SQL searches: Auth references are `auth.uid()` calls and foreign keys to `auth.users`; there is no Auth-targeting INSERT/UPDATE/DELETE/TRUNCATE, and the sole dynamic DDL loop names only five public business tables. This is source-review evidence for this pinned corpus, not a general SQL sandbox or permission to trust future migration changes without new review. No Auth rows or tokens were selected in the fixture. [Final review disposition](evidence/MP-08g-review-disposition.json) records this boundary.

The next MP-08e slice can design a private session table and narrow trusted transactional access against this measured schema. It must still prove active-profile/provider expiry, credential encryption, concurrent refresh fencing, revocation, provider denial and real Auth HTTP behavior. This fixture does not certify those behaviors or a production-ready session authority. Supabase's [Auth self-hosting guidance](https://github.com/supabase/auth/blob/master/README.md) cautions against modifying its managed schema; the application migrations remain public-only.
